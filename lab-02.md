## 1. Мета роботи

Розібратися, як влаштовані ERP- і CRM-компоненти, на прикладі коробкової системи Odoo. Перевірити fit-gap аналізом, яку частину вимог «КавоХаб» для вашого модуля вона покриває, і обґрунтувати рішення «купити / налаштувати / розробити». Потім спроєктувати ядро власного модуля: доменну модель, життєвий цикл документа, довідники, бізнес-правила, схему зберігання, API та тестові сценарії для тих вимог, які коробка не покрила. Код не пишеться — здається проєкт, за яким модуль можна реалізувати.

## 2. Результати

Після виконання роботи студент уміє:

- аналізувати функціональність модулів коробкової ERP/CRM (довідники, воронку, цінові правила, склади, рахунки) і відображати на неї наскрізний процес;
- проводити fit-gap аналіз і обґрунтовувати рішення «купити / налаштувати / розробити» в ADR;

- описувати життєвий цикл документа як скінченний автомат;
- специфікувати бізнес-правила, схему БД, REST API з помилками у форматі RFC 9457 і набір тестових сценаріїв.

## 4. Короткі теоретичні відомості

### 4.1. Документ і його життєвий цикл

Основа обліку в КПС — документ (замовлення, резерв, відвантаження, рахунок). Документ має життєвий цикл — скінченний автомат зі станами й дозволеними переходами. Переходи виконуються лише командами (`confirm`, `ship`, `issue`), а не довільною зміною поля `status`. Після «проведення» документ не редагується: помилку виправляє новий документ (коригування, сторно, кредит-нота). Це вимога і обліку, і аудиту.

### 4.2. Основні дані (master data) і транзакційні дані

Довідники (клієнти, товари, склади, ціни) змінюються рідко і використовуються багатьма документами. Транзакційні дані (документи й рухи) з'являються постійно, і їх не можна видаляти. У «КавоХаб» кожен довідник має власника (`README.md`, розділ 2.5). Модуль, що не є власником, тримає лише репліку для читання.

### 4.3. Внутрішня структура модуля

Рекомендована структура — гексагональна (ports & adapters), див. Л3, ч. 2. У проєкті її показують діаграмою C4 Component (з ЛР1) і розподілом відповідальностей:

```text
<module>/
├── domain/          # сутності, об'єкти-значення, автомати станів, бізнес-правила — без фреймворків і БД
├── application/     # сценарії (команди і запити), транзакції, порти (інтерфейси репозиторіїв, шлюзів)
├── adapters/
│   ├── in/http/     # REST-контролери, валідація, мапінг помилок у Problem Details
│   └── out/db/      # реалізації репозиторіїв, міграції
│   └── out/odoo/    # адаптер до Odoo (якщо модуль із нею інтегрується)
└── tests/           # модульні тести домену без БД; інтеграційні — у ЛР6
```

Правило залежностей: `domain` не імпортує нічого з `application` і `adapters`.

**Агрегат** — кластер об'єктів, який змінюється однією транзакцією і захищає свої **інваріанти** (правила, що завжди істинні, наприклад «сума замовлення = сума рядків»). Зовні на агрегат посилаються лише за ідентифікатором кореня.

### 4.4. Гроші, кількості, дати

- Гроші — тип `decimal` у коді та `numeric(14,2)` у БД. Тип `float` для грошей заборонений.
- ПДВ (20 %) обчислюється по рядку з округленням до копійок за правилом «половина — вгору»; сума документа дорівнює сумі рядків.
- Кількість: штуки — ціле число; кілограми — `numeric(12,3)`.
- Дати документів — дата в часовому поясі `Europe/Kyiv`; моменти подій (timestamps) — в UTC.

### 4.5. Помилки API у форматі RFC 9457

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://kavohub.example/problems/invalid-transition",
  "title": "Недопустимий перехід стану",
  "status": 409,
  "detail": "Замовлення ORD-2026-004213 у стані 'shipped' не можна скасувати",
  "instance": "/orders/ORD-2026-004213/cancel",
  "currentState": "shipped",
  "allowedActions": []
}
```

У «КавоХаб» прийнято єдиний для всіх модулів перелік `type` типових помилок: `validation-error` (422), `not-found` (404), `invalid-transition` (409), `conflict` (409), `forbidden` (403), `approval-required` (409). Нові `type` для свого модуля можна додавати, але з обґрунтуванням у журналі рішень.

### 4.6. Зовнішній API Odoo

Спосіб доступу залежить від версії Odoo (перевірте документацію External API своєї версії):

- **Odoo 19 і новіші — JSON-2 API.** API-ключ створюється в профілі користувача і передається в заголовку `Authorization: bearer <ключ>`. Аргументи методу — іменовані, у JSON-тілі. XML-RPC і JSON-RPC у цих версіях позначено застарілими, видалення анонсовано для Odoo 22.

```http
POST /json/2/res.partner/search_read
Authorization: bearer <ODOO_API_KEY>
Content-Type: application/json

{"domain": [["is_company", "=", true]], "fields": ["name", "vat", "city"], "limit": 5}
```

- **Odoo 18 і старіші — XML-RPC**: `/xmlrpc/2/common` для автентифікації, `/xmlrpc/2/object` для викликів `execute_kw(db, uid, key, model, method, args, kwargs)`.

Основні моделі: CRM — `res.partner`, `crm.lead`, `crm.stage`; Sales — `sale.order`, `sale.order.line`, `product.pricelist`; Inventory — `product.product`, `stock.quant`, `stock.picking`, `stock.warehouse`; Invoicing — `account.move` (рахунки, кредит-ноти), `account.move.line`, `account.payment`, `account.journal`.

## 6. Завдання

### 6.1. Частина A. Системне завдання: Lead-to-Cash в Odoo

Разом із чатом пройдіть процес Lead-to-Cash «на папері» за документацією Odoo і опишіть, як кожен крок виконувався б у застосунках CRM, Sales, Inventory, Invoicing:

1. **CRM:** лід «Кав'ярня "Зерно"» → кваліфікація → нагода (opportunity) → воронка до «Виграно».
2. **Sales:** комерційна пропозиція (quotation) на 10 кг кави і кавомолку зі знижкою 12 % → підтвердження замовлення.
3. **Inventory:** резерв → відвантаження (delivery order).
4. **Invoicing:** рахунок за відвантаженими кількостями → проведення → часткова і повна оплата → кредит-нота на 1 кг.

Результат — таблиця «крок → застосунок і модель Odoo → що відбувається → що не сходиться з вимогами ЛР1». Детально опишіть кроки, що стосуються вашого модуля; решту — одним рядком. Обов'язково дайте відповідь: що сталося б зі знижкою 12 % — чи вимагала б система погодження?

### 6.4. Частина A. Завдання за модулем: проєкт адаптера до API Odoo

Спроєктуйте, як ваш модуль читає або записує дані в Odoo (для Billing — обов'язково; адаптер буде основою інтеграції в ЛР3; для інших модулів — читання довідника свого модуля для порівняння чи початкового імпорту):

1. Версія Odoo і спосіб доступу (JSON-2 чи XML-RPC) з обґрунтуванням з урахуванням анонсованого видалення XML-RPC.
2. Таблиця операцій: операція адаптера → модель Odoo → метод (`search_read`, `create`, `write`, `action_post` тощо) → ключові аргументи.
3. Мапінг полів: поле моделі «КавоХаб» → поле Odoo → перетворення (одиниці, валюта, ідентифікатори, ПДВ).
4. Антикорупційний шар: які поняття Odoo не мають проникати в домен вашого модуля і як адаптер їх ховає.
5. Обробка збоїв: недоступність API, ліміт запитів, повторний виклик (як не створити дубль запису в Odoo).
6. Приклад одного запиту й відповіді (JSON або псевдокод `execute_kw`) як ілюстрація.

Довідники: CRM — `res.partner`, `crm.lead`; Orders — `sale.order`, `product.pricelist`; Inventory — `product.product`, `stock.quant`; Billing — `account.move`, `account.payment`; Notifications / Reporting — `mail.template`, `account.move` (для PDF рахунку).

### 6.5. Частина A. Системне завдання: ADR-0004 «Buy vs build»

На основі своєї fit-gap таблиці та обговорення з чатом у ролі команд інших модулів напишіть ADR: що «КавоХаб» бере з Odoo, а що розробляє, і чому. Детально обґрунтуйте частину, що стосується вашого модуля; для інших модулів достатньо позиції, яку «озвучила» відповідна команда. Обов'язково розгляньте варіант «усе в Odoo + власні модулі Odoo» і опишіть, що станеться з розширеннями під час переходу на наступну версію Odoo.

### 6.6. Частина B. Загальні вимоги до проєкту модуля

1. **Доменна модель:** діаграма класів або ER у Mermaid/PlantUML; агрегати з коренями, їхні інваріанти; позначення сутностей і об'єктів-значень; репліки чужих даних (позначити джерело, README 2.5).
2. **Автомат станів** основного документа: діаграма станів + таблиця переходів (стан, команда / подія, умова, роль, новий стан, побічні ефекти — подія, резерв тощо).
3. **Бізнес-правила** з таблиці свого варіанта (розділ 6.7): для кожного — де саме перевіряється (агрегат, сценарій застосунку, обмеження БД) і яку помилку повертає порушення.
4. **Схема зберігання:** таблиці своєї схеми (`crm`, `orders`, `inventory`, `billing`, `notifications`) з типами, ключами, обмеженнями (`CHECK`, `UNIQUE`), індексами — як фрагмент DDL або таблиця; план міграцій (які міграції й у якому порядку); склад невеликого чистого набору seed-даних (5 клієнтів, 20 товарів, 2 склади, базовий прайс). «Брудна» міграція — у ЛР5.
5. **REST API:** таблиця ендпоінтів (метод, шлях, призначення, роль, тіло запиту, успішна відповідь, можливі помилки з `type` і кодом) для довідників і команд переходів; 2–3 приклади запитів і відповідей, з них щонайменше одна помилка RFC 9457. Формальний OpenAPI-контракт — у ЛР3.
6. **Тестові сценарії** як специфікація: не менше 10 сценаріїв у форматі Given / When / Then з посиланням на правило; щонайменше один сценарій перевіряє всі заборонені переходи автомата (таблиця «стан × команда → дозволено / помилка»); для правил конкурентного доступу — сценарій із паралельними запитами.

## 7. Етапи роботи з чатом

### Етап 1. Odoo і Lead-to-Cash (≈ 1 год)

Обговоріть із чатом, як процес Lead-to-Cash відображається на застосунки й моделі Odoo (6.1), і пройдіть аналіз свого застосунку (6.2). Чат пояснює поведінку Odoo, а в ролі стейкхолдерів відповідає на запитання про налаштування «КавоХаб» (факти 5.1).

Етап завершено, коли: є таблиця Lead-to-Cash в Odoo і відповіді на всі запитання «Що з'ясувати» з підставами.

Приклади запитів:

```text
Ось як я розумію крок 2 в Odoo Sales: <опис>. Що я пропустив і що станеться зі знижкою 12 %?
Хочу запитати Олега Савчука, яку версію Odoo використовує партнер і чи можна отримати доступ до API.
```

### Етап 2. Fit-gap, адаптер, ADR-0004 (≈ 1 год)

Складіть fit-gap таблицю (6.3) і попросіть чат-рецензента перевірити кожен висновок. Спроєктуйте адаптер до API Odoo (6.4). Обговоріть ADR-0004 (6.5) з чатом у ролі команд інших модулів і архітектора.

Етап завершено, коли: fit-gap має 8–10 рядків з підставами, адаптер описано (операції, мапінг, збої), ADR-0004 має щонайменше три варіанти й наслідки для оновлень.

Приклади запитів:

```text
Перевір мою fit-gap таблицю: де я класифікував як Configure те, що насправді вимагає Extend?
Будь командою Orders: чи погоджуєтеся ви, що погодження знижок не робимо в Odoo? Які у вас заперечення?
```

### Етап 3. Доменна модель і автомат станів (≈ 1,5 год)

Запропонуйте агрегати, їхні інваріанти, сутності й об'єкти-значення для свого варіанта (6.6, п. 1; 6.7). Побудуйте автомат станів основного документа (п. 2). Чат-рецензент шукає порушені інваріанти, зайві зв'язки між агрегатами, пропущені переходи й ролі.

Етап завершено, коли: є діаграма доменної моделі, діаграма й таблиця переходів, і для кожного бізнес-правила визначено місце перевірки (п. 3).

Приклади запитів:

```text
Ось мої агрегати: <список>. Чи правильно, що Reservation — окремий агрегат, а не частина StockItem?
Знайди в моїй таблиці переходів стан, з якого неможливо вийти, і перехід без ролі.
```

### Етап 4. Зберігання, API, тестові сценарії (≈ 1,5 год)

Спроєктуйте схему своєї БД і план міграцій (п. 4), таблицю API з помилками RFC 9457 (п. 5), тестові сценарії (п. 6). Попросіть чат у ролі QA знайти правила без тестів і сценарії конкурентного доступу, які ви пропустили.

Приклади запитів:

```text
Ось DDL моєї схеми. Які інваріанти з доменної моделі не захищені обмеженнями БД і чи це нормально?
Будь QA: які з моїх 10 сценаріїв дублюють один одного, а якого негативного сценарію бракує?
```

Попросіть чат провести самоперевірку за критеріями (розділ 10), захист за контрольними питаннями (розділ 11, щонайменше 5) і допомогти зібрати документ (README, розділи 3.5 і 6.2).

## 11. Контрольні питання

Чат ставить на захисті щонайменше 5 із них, обираючи ті, що стосуються вашого модуля.

1. Чим «Configure» відрізняється від «Extend» у fit-gap аналізі? Чому «Extend» дорожчає з кожним оновленням версії?
2. Яку вимогу «КавоХаб» Odoo покриває найкраще, а яку — найгірше? Чим ви це підтвердили?
3. Чому Odoo в «КавоХаб» залишається системою запису для бухобліку, хоча вона вміє вести і CRM, і склад?
4. Навіщо адаптеру до Odoo антикорупційний шар? Які поняття Odoo ви не пустили в домен свого модуля?
5. Чому переходи стану виконуються командами, а не оновленням поля `status`? Яку помилку і з яким кодом поверне ваш API на заборонений перехід?
6. Чому гроші не можна зберігати у `float`? Наведіть приклад помилки округлення.
7. Чому `SEQUENCE` у PostgreSQL не гарантує безперервної нумерації рахунків? Як би ви розв'язали цю задачу?
8. Як ваш модуль запобігає подвійному резервуванню останньої одиниці товару (або подвійному зіставленню платежу, дублю клієнта, дублю повідомлення)?
9. Що в доменній моделі вашого модуля є сутністю, а що — об'єктом-значенням? Які межі агрегатів ви обрали і чому?
10. Які інваріанти ви захищаєте обмеженнями БД, а які — лише в домені? Чому?
